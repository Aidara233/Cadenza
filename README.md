# CADENZA · Lilara 的舞台

> 版本 1.1.0 · 华彩乐段：乐队停下，独奏者即兴。你指挥，它演奏。

Cadenza 是 Lilara 核心（`AgentLilaraCode`）的浏览器前端，照 `../09-控制面API参考.md` 实现。

**连核心的是 Cadenza 的进程，不是浏览器**（用户裁定 2026-11-14）：页面只跟**一个源**说话——
`serve.ps1` / `serve.sh` 那台宿主，它把 `/core/*` 原样转给核心（HTTP 快照、`/store` 的字节、
一条 WebSocket 全走这条路）。所以这个头**不再是纯静态服务器**，而是一层薄反代：
它不缓存、不理解业务，但它握着凭据、也替页面挨白名单那一关。详见下面「谁在连核心」。
直连仍然留着（`?core=http://…`，以及 php / busybox 那两条退路），那是排错时的对照面。

零依赖、零构建：`index.html` + 原生 ES 模块 + 四份 CSS。没有 npm，没有 CDN，没有联网资源。

## 启动

```bash
# 1. 起核心（端口 17988；默认监听 0.0.0.0；每次启动都把访问 token 打印在横幅里——见「访问 token」）
#    发布的单文件版（见 AgentLilaraCode/publish）或从源码 dotnet run 都行
cd E:\Workspace\AgentLilaraCode\src\Lilara.Core && dotnet run -c Debug

# 2. 起 Cadenza（页面宿主 + 反代，默认 17990）。页面**经它**连核心，所以核心那边
#    不用为了这个端口去改白名单；核心开了鉴权就把 token 交给它（-Token / --token）。
#    Windows：
powershell -NoProfile -ExecutionPolicy Bypass -File Cadenza\serve.ps1
#    macOS / Linux / WSL / Git Bash：
./Cadenza/serve.sh
```

两个脚本是**同一份契约的两个实现**（参数名、默认值、启动自检、报错措辞对齐；改一个必须改另一个）：

| 参数 | `serve.ps1` | `serve.sh` | 说明 |
|---|---|---|---|
| 端口 | `-Port 17991`（或 `LILARA_HEAD_PORT`） | `--port 17991`（或 `LILARA_HEAD_PORT`） | |
| 上游核心 | `-Core http://…`（或 `LILARA_CORE`） | `--core http://…`（或 `LILARA_CORE`） | **本进程替页面连的那个核心**（默认 `127.0.0.1:17988`）。与页面里的 `?core=` 是两件事 |
| 核心 token | `-Token <token>`（或 `LILARA_CORE_TOKEN`） | `--token <token>`（或 `LILARA_CORE_TOKEN`） | 核心开了 `LILARA_AUTH=1` 时；配了它页面就一条凭据都不带 |
| 监听地址 | `-Bind 127.0.0.1`（默认 `0.0.0.0`；或 `LILARA_HEAD_BIND`） | `--bind 127.0.0.1`（默认 `0.0.0.0`；或 `LILARA_HEAD_BIND`） | |
| 根目录 | `-Root …` | `--root …` | |
| 跳过自检 / 不打开浏览器 | `-NoCheck` / `-NoOpen` | `--no-check` / `--no-open` | |
| 只开浏览器 | — | `--open-only` | |

**监听地址默认是 `0.0.0.0`（对局域网开放）** —— 和核心 2026-11-05 那个裁定一致：同一网络里的
手机/平板直接打开页面，而不是默认不可用。要收回本机：

```bash
./serve.sh --bind 127.0.0.1
powershell ... -File Cadenza\serve.ps1 -Bind 127.0.0.1
```

⚠️ **Windows 上多一步（只有 `serve.ps1` 有这道坎）**：它走 `HttpListener`，绑回环之外的前缀需要一条
URL ACL，没有它 `Start()` 报「拒绝访问」（这台机器上实测如此）。先跑一次（管理员）：

```
netsh http add urlacl url=http://+:17990/ user=<你的用户名>
```

`serve.ps1` **不会因此起不来**：它会印出上面那条命令（带你的用户名）然后**退回仅本机**继续服务，
横幅里明说「退回：0.0.0.0 被 Windows 拒绝」——在那之前页面在本机能用、手机连不上。
macOS / Linux 上的 `php -S` / `python3` 没有这个概念，默认就直接对局域网开放。

⚠️ **反过来的坑（本机实测，2026-11-05）**：一旦端口上有了那条 `http://+:17990/` 保留，
`http://127.0.0.1:17990/` 就**再也绑不上**了（拒绝访问）——http.sys 只放行 `+`。
所以「加了 ACL 之后又想 `-Bind 127.0.0.1` 收回本机」是行不通的，得先删掉那条保留：
`netsh http delete urlacl url=http://+:17990/`（管理员）。`serve.ps1` 遇到这种局面会把这条命令
和「这条保留属于谁」一起印出来，不再谎报成「端口被占」。
一句话：**`+` 与 `127.0.0.1` 二选一**（前者是默认值，能对局域网开放；后者不需要任何 ACL）。

`/config.json`（页面启动时读它拿**连法**）交的是「怎么连」而不是「核心在哪」——它跟着这条链走：
反代时交 `{proxy, upstream, auth, wsProtocol}`（页面只跟本页的源说话），退化成直连时交
`{core: …}`（老形状，值跟着**请求的 Host** 走：写死 `127.0.0.1` 的话手机打开页面会去连
**手机自己**，而症状与「核心没起来」完全一样）。逐字见上面「谁在连核心」。

两个脚本都会**自动打开浏览器**（`--no-open` / `-NoOpen` 关掉）；自动化（e2e）就是靠这个开关
避免在跑测试时弹出窗口。

`serve.sh` **不内置** HTTP 服务器——它按顺序挑这台机器上现成的。⚠️ 这里有一条**硬约束**：
反代要能同时转 HTTP 与 **WebSocket 隧道**，所以顺序不是「哪个最常见」而是「哪个做得到」：

| 顺序 | 服务器 | 能做到什么 |
|---|---|---|
| 1 | `python3` + `serve.py` | **完整**：静态 + `/core` HTTP 反代 + WS 隧道（token、白名单那些好处全在这儿） |
| 2 | `php -S` + `serve-router.php` | 只静态 + **页面直连核心**（`php -S` 单线程、拿不到已接受连接的原始套接字 ⇒ 撑不起长命的 WS 隧道） |
| 3 | `busybox httpd` | 同上，且**不关缓存**、**没有 `/config.json`** ⇒ 页面退回默认核心地址 `127.0.0.1:17988` |

落到第 2/3 档时它会把「为什么没有反代、装什么能拿到」印出来，而不是静默降级。三个都没有时
它会明确说明装哪一个。

> ⚠️ 发布的核心单文件**不含前端**：`Cadenza/` 目录要跟着一起分发（它本来就是零构建的静态文件）。
> 头可以指到别处的核心（`--core`）；跨机器时**只有反代这一档**是真的省心：核心的白名单
> （默认模式 `http://*:<头端口>`）与 token 都由头那一侧处理，别的设备只要连得上头就行。
> 直连那一档还是老规矩：白名单要吻合（`LILARA_ALLOWED_ORIGIN` 可钉死主机），核心开了鉴权时页面要填 token。

打开 **`http://127.0.0.1:17990`**（`localhost:17990`、局域网 IP、隧道地址都行）。
反代模式下**地址随你怎么打开**：握手是进程发的，核心那边的白名单根本用不上（见下一节）。
直连模式下才回到老规矩——白名单按**端口**认、主机名不参与，端口对不上时握手会被静默拒绝，
页面会拉 `/info.allowedOrigin` 并在顶部横幅写清是哪个端口；那句判断来自同一份判据
（`js/core.js` 的 `originMatches`）。

### 谁在连核心（页面 → 进程 → 核心）

用户裁定 2026-11-14：**由 Cadenza 的进程连核心，而不是浏览器的页面。** 具体是这样一条链：

```
浏览器 ──同源──▶ Cadenza 的进程（serve.ps1 / serve.py）──▶ 核心（HTTP + WS）
   ▲  静态文件、/core/* 都在这一个源里          ▲ 不带 Origin、带 Bearer（可选）
```

| | 直连（旧形态，仍在） | 反代（默认） |
|---|---|---|
| 页面打哪儿 | 核心的地址（`http://127.0.0.1:17988`） | 本页的源 + `/core`（`/core/info`、`/core/ws`） |
| 谁发 WS 握手 | 浏览器（**带** `Origin` ⇒ 要过核心的白名单） | 进程（**不带** `Origin` ⇒ 核心一律放行） |
| token 谁交 | 页面（本机存储 + token 闸 + `?token=`） | 进程（`-Token` / `LILARA_CORE_TOKEN`），页面一条都不带 |
| 换设备 / 换地址 / 上隧道 / 上 https | 要给核心改 `LILARA_ALLOWED_ORIGIN` | 不用动核心 |
| 怎么进这一档 | `?core=http://…`、存着 `core`、php / busybox 那两条退路 | `/config.json` 里带 `proxy` |

`GET /config.json`（页面启动时读一次）就是这两档的开关，也是**头与页面之间的契约**：

```jsonc
// 反代（serve.ps1 / serve.py 默认）
{ "proxy": "/core", "upstream": "http://127.0.0.1:17988",
  "auth": "head",              // head = 进程交 token；page = 页面自己交（进程没配 token 时）
  "wsProtocol": "cadenza" }    // 头要求页面带的 WS 子协议，见下面那条 ⚠️
// 直连（php / busybox / 任何静态服务器）
{ "core": "http://192.168.1.5:17988" }
```

几条**必须**知道的：

- **`/core` 前缀不是装饰**：核心的路径只有加上它才通（`/core/info`、`/core/store/{sha}`、`/core/ws`）。
  不加就是头自己静态目录里的 404——这正是「反代真的在转」与「页面其实直连」的分界。
  HTTP 的状态码与**响应体**都原样交回（页面的 token 闸、`HttpError` 上那句人话理由全靠它）。
- ⚠️ **WS 子协议 `cadenza` 是 Windows 那台头的硬约束**：`HttpListener.AcceptWebSocketAsync`
  只接受「客户端**确实请求过**」的子协议，所以页面在反代模式下是 `new WebSocket(url, "cadenza")`。
  直连模式**一个子协议都不带**（核心不需要；客户端请求了而服务端不选，浏览器会直接失败）。
  这解释了为什么 `js/core.js` 里那行 `new WebSocket` 有两种形状——不是疏漏。
- ⚠️ **进程必须并发处理请求**：一条 WS 是全命运的（页面开着就一直占着），而 `HttpListener`
  的 `GetContext()` 是单线程的。`serve.ps1` 因此把每个连接扔进一个 **runspace pool**，
  主循环只收连接。写在主循环里的话，页面加载完就再也请求不动任何东西（看起来像「头死了」）。
- ⚠️ **WS 失败在页面上看不见**：浏览器不把握手失败的响应体交给 JS。所以头把上游的拒绝原因
  打在**自己的控制台**上（`! 上游 WS 拒绝：…`），页面那边只表现为「已断开 · 重连中」。
- **上游只由头决定**：`-Core` / `--core`（默认 `127.0.0.1:17988`）才是核心地址。页面里的
  `?core=` 是「让**页面自己**去连那个地址」（直连，排错用），与头无关。
- 反代**不缓存、不理解业务**，只多两件事：带上凭据、转交字节。它不重写 `Host`、不加 CORS 头
  （同源了，不需要）。

### 访问 token

核心（`LILARA_AUTH=1` 时）会校验一个**每次启动重新生成**的 token，并把它打印在自己控制台的启动横幅里
（`访问 token …` 那一行）。默认**不校验**——那时 token 照样打印，只是没人问。

**这份 token 归谁交，取决于走哪条路**（`/config.json` 的 `auth`）：

| `auth` | 什么时候 | 谁带凭据 | 页面能做什么 |
|---|---|---|---|
| `page`（旧形态，也是反代进程没配 token 时的形状） | 核心开了鉴权而进程没拿到 token | **页面**：本机存储 + token 闸 | 弹闸、粘进去、重载 |
| `head` | 进程拿到了 token（`-Token` / `LILARA_CORE_TOKEN`） | **进程**：每条转发出去的请求都带 `Authorization: Bearer`（WS 握手也是**请求头**，不是 `?token=` —— 它不再是浏览器了） | 什么都不用做；换 token 要重启进程 |

所以「token 进不进浏览器」是一道选择，不是既定事实。**推荐 `head`**：凭据只在一个进程的内存里，
不落 localStorage、不出现在 URL 里、也不用在每台设备上各填一遍。

页面侧（`auth=page` 时）的细节：

| | 怎么做 |
|---|---|
| HTTP | 每条请求都带 `Authorization: Bearer <token>`（`core.js` 的 `_req`，一处出口；反代模式下这一条经 `/core` 转给核心） |
| WebSocket | 只能走查询参数 `?token=<token>`——浏览器的 `WebSocket` 构造函数**不能自定义请求头**（进程那边没有这个限制，它走头） |
| 图片 / 库链接 | `<img src>` / `<a href>` 同样只能走查询参数（`blocks.js` 的 `storeUrl`）；`auth=head` 时**一个参数都不加** |
| 存在哪 | 本机存储 `cadenza.token`（刷新不用重填；清掉就是「没有 token」） |
| 怎么填 | 页面自己铺一层闸（`.token-gate`）：粘进去 → 保存 → 整页重载。后台「系统」页也有同一格，用于换 / 清 |
| 401 | 一律先**清掉**存着的那份再弹闸：核心每次启动都换 token，昨天那份今天必然失效 |
| 401（`auth=head`） | **不弹闸**（页面填什么都没用）：横幅让你把新 token 交给进程再重启 Cadenza |
| 没有 `/info` 也一样 | `/info` 是唯一豁免鉴权的端点；未授权时它**照样回 200**，只是少了 `dataRoot` / `workingDirectory` 那几格，并多一个 `authRequired: true` |

⚠️ **代价说清楚**：控制面是明文 HTTP。token 拦得住「随手连上来的人」，挡不住同一网段里的嗅探者；
它是「谁都能用」与「谁都不能用」之间的一道闸，不是加密。要真的防嗅探，得上 TLS 或隧道。
⚠️ 反代之后**这条代价变重了一点**：头替页面连核心，等于「能打开这个页面的人」都能经 `/core`
驱动核心（以前至少还要过核心那道白名单）。头的 `-Bind 0.0.0.0` 是对局域网开放的——要么收回本机，
要么让核心开鉴权、把 token 交给头。

和 Aquarius 用同一个默认端口，两个头同时开要给其中一个换端口。

| II | **总谱** | WS 每一帧（过滤 / 方向 / 暂停 / 原始 JSON）+ 命令台：25 条命令全覆盖（含计划编辑、模型目录查询与后台任务三条），表单或原始 JSON |
| III | **账簿** | token 账本：五个总数、逐次调用的堆叠柱图（缓存读 / 输入 / 输出同柱，自下而上）、按天堆叠、按模型 / 提供商拆分、明细（点开看原始记录），历史载入条数可填 |
| IV | **后台** | 提供商增删改 + 试音（含每个提供商单独的**调用超时**），系统提示词预设，**联网配置**（启用 / Tavily key / 端点 / 上限 / 域名白名单 / 试搜），**Shell 配置**（总开关 / `sh` 路径或自动探测 / 超时 / 试一下），系统自检（版本 / 数据根 / WS 白名单吻合与否 / 原始端点） |

顶栏那条谱**只有一条**：音符 = 会话真的做了什么（起步 / 等你 𝄐 / 完成 / 出错 ✕ / 重试 / 压缩 / 目标切换），
越靠上越需要你看一眼（顶线＝等你或出错的邻居，底线＝跑完一轮），♩ = 每分钟行为数；
网络帧退成谱面后的淡竖线，同一族 260ms 内连发合并成一根，越密越亮越粗。悬停可看详情；右下角 ♪ 打开音量面板（默认关闭，主音量 + 每个音各自一段，命令面板里也有同一入口）。

谱右边那几格是**顶栏的运行状态**（`js/runstate.js`，跟着视图走，切到总谱 / 账簿 / 后台也还在）：

| 格子 | 什么时候出现 | 说什么 | 点了 |
|---|---|---|---|
| `♩ 标题 谱曲 12.3s` | 打开了某个会话 | 当前这一场的相位（谱曲 / 排练 / 候场 / 休止）+ 这一段已跑多久 | 回舞台 |
| `✕ N 个出错` | 别的会话上一步失败了 | 几个（Hover 看是哪几场、什么原因） | 跳到第一场 |
| `♩ N 演奏中` | 别的会话还在跑 | 几个（Hover 看是哪几场、各自什么相位） | 节目单 |
| `⏳ N 在跑` | 当前会话有后台任务在跑 | 与舞台头部那格**同一个数** | 任务面板 |
| `⚑ 目标` | 主动性轴拨到了 `goal` | —— | 舞台 |

⚠️ 这几格**不存第二份状态**：相位读 `phaseOf`、时长读行的 `runSince` / `runElapsedMs`
（判据在 `model.js` 的 `runtimeText`，节目单用的是同一个）、任务数读 `mixer.jobsSummary`
（唯一去拉那张表的还是调音台）。所以「顶栏说在跑、节目单说休止」在结构上不会发生。
当前这一场不重复数进「演奏中 / N 个出错」——它自己那一格已经把话说完了。
窄屏按 1280 / 1100 / 900 三档收：先收「演奏中 / 任务 / 目标」，再收标题，只留「哪一场 · 什么相位 · 跑了多久」。
浏览器标签题报的是**全局**（`paintTitle`，**一个写者**：`app.js` 只画那颗「等你」按钮，不碰 `document.title`）：

```
✕N 出错  →  𝄐N 等你  →  ✓N 完成  →  ⏳N 任务  →  ♩N 在跑  · Cadenza
```

例 `✕1 出错 · 𝄐2 等你 · ♩1 在跑 · Cadenza`。顺序就是优先级，也正好是**截断时的保留顺序**
（标签只露前十几个字）：有在跑就报几个在跑，有出错 / 等你 / 刚跑完的就先报那几个。
每个数只在 >0 时出现；全空时退回品牌全名 `Cadenza · Lilara`（静止时与以前逐字相同）。
口径：`✕` 读行的 `lastError`（下一步起步时自己清）、`𝄐` 与「等你」按钮同一个数、`✓` 读行的
`doneAt`（跑完还没打开看过，打开就清）、`⏳` 是当前会话的后台任务（核心的任务清单按会话给，
别处拿不到）、`♩` 数相位落在谱曲 / 排练的会话（候场不算「在跑」，它的出口是那个 `𝄐`）。
出错的那几场从「在跑 / 完成」里摘掉——同一场不在标签上数两遍。
⚠️ `✓` 与节目单的「待查看」是同一个字段，也带着同一条限制：头部要从**订阅着的**会话流里听见
相位落回 Idle，才不会漏掉「刚跑完」；从没打开过的会话要等一次 `/sessions` 刷新（≤15 秒）才订阅得上。

节目单里「刚跑完、还没打开看过」的会话会一直亮着（行尾一行「待查看」）：点开它就熄灭——
打开就是「检查过进度」这个动作，不按时间自动消失。

快捷键：`Ctrl+K` 命令面板 · `Alt+1..4` 切视图 · `Alt+N` 新会话 · `/` 聚焦输入框 · `Enter` 发送 / `Shift+Enter` 换行。草稿按会话存本机。

## 手机 / 窄屏

一屏只站得下一个栏，所以窄下来不是「把桌面缩小」，是换一套**导航**：

| 宽度 | 变化 |
|---|---|
| ≤1280 | 三栏一起收窄（250 / 1fr / 300） |
| ≤1080 | 调音台收成右侧抽屉（头部 `𝄢` 拉开、点遮罩或 Esc 收起） |
| ≤760 | **屏栈**：会话屏之外，节目单 / 调音台 / 概览各是一整个屏；视图切换搬到**底部 tab bar** |
| ≤640 | 顶栏只留「← / 屏名（或标记）/ 等你 / ⌕ / 连接点」；输入框 16px；触控目标 32–40px |

手机上的舞台是一条屏栈（`#stage` = 会话屏，`#stage/list` / `#stage/mixer` / `#stage/about` = 二级屏）：

- **会话屏**（根）：头部只剩「标题 + 状态 · 相位 + ☰ 𝄢 ⋯」。项目 / id / 模型 / 回合 / 父子会话 /
  工作目录 / 归档这些「看一眼才需要」的东西搬进了**概览屏**，连同全部动作（推进 / 压缩 / 回收 /
  复制 id / 快照 / 归档 / 删除）。只有真有事的两格（后台任务在跑、目标进行中）还留在头部。
- **节目单**（☰）：整页，一行一场会话，点了就回会话屏。
- **调音台**（𝄢）：整页，轴 / 槽位 / 工具 / 任务的页签横排在浏览器宽度上就放得下——这是屏栈最大的一处收益。
- **概览**（⋯）：元信息 + 动作两栏网格。
- 顶栏那颗 `←` 回上一层，Android / 浏览器的返回键同样能逐层退（二级屏用 `pushState` 进栈）。
- 底部 tab bar 切四个视图；点已经亮着的「舞台」= 回到会话屏。

几条手机上必须做的事：

- **`100dvh` 而不是 `100vh`**：地址栏收起/展开会改可视高度，用 `vh` 会让底部那条导航被盖掉一截。
  配 `viewport-fit=cover` + `env(safe-area-inset-*)`，顶栏 / 底部 tab bar 各自吃掉自己的刘海与 home 指示条。
- **输入框一律 16px**：iOS 在 <16px 的输入框上聚焦会把整页放大并且不缩回来。`.composer-inp` 的这条在
  `stage.css`（那里有同名的 shorthand，而 `stage.css` 在 `base.css` 之后加载）。
- **屏栈不是抽屉**：≤760 用 `[data-screen]` 整屏切换（`display` 切，不做滑动），≤1080 才用
  `transform` 的抽屉 + 遮罩；两套形态共用一个 `setStageScreen()`，不各判一次宽度。
- **hash 只有一个写者**：舞台的入口按钮只 `emit("screen")`，`app.js` 负责 `pushState` / `replaceState`
  与顶栏那颗 `←`。两处各写一半，返回键的栈迟早会乱。
- ⚠️ **启动时只有「舞台」那一支写 hash**：`applyStageScreen` 写的永远是 `#stage…`，在 `#greenroom` /
  `#score` / `#ledger` 上启动时调它，等于把地址改回舞台——**刷新一次就退回舞台**，而且那个一级视图
  一次都不渲染（`2-flow` 的 reset 正是一次 `location.reload()`，回来找不到后台页上的 `.prov-new`）。
  ⇒ 启动那一处传 `hash: false`，把「哪一屏」与「地址写什么」分开。
- **`overscroll-behavior: none` + `touch-action: manipulation`**：在消息流里往上滑不会把整页刷了，双击也不缩。
- 窄到一栏时输入框的 placeholder 只说「写下下一句…」——`Enter 发送 / Shift+Enter 换行` 在手机上不成立。

## 协议上的取舍

- 打开会话：先 `GET /state` 拿 `highWater` → `subscribe(session:id, since)` → 拉历史。中间落下的事件靠补发，重复的靠幂等键去掉（`message.appended` 按 `historyId`，`tool.result.appended` 按 `id`）。
- `resync_required` 或断线重连 ⇒ 重新拉快照、重新订阅，不做部分合并。
- `accepted:true` 只代表受理；业务失败看 `error` 事件，画成「不和谐音」记号。
- 授权批准发 `answers.decision:"allow"`；改写过参数才带 `answers.arguments`（只换排版的 JSON 不算改写）；`remember` 只发 `"args"` / `"tool"`。
- 有询问在等时直接发消息会先确认——核心会把那次询问顶替掉（`superseded`）。
- `GET /sessions` 的 `ask` 判 `ask?.askId`；`title` 缺省；用量里的 `null` 显示 `—`，不当 0 加。
- **会话状态只有一份**：`model.js` 的 `onGlobalEvent` 是唯一的折叠口，节目单、顶栏运行状态、标题栏、演奏条、
  中断键、等你按钮、状态栏、命令面板都从同一行读。`session.state` / `step.*` / `error` / `retry.attempt`
  只发在会话流上，所以**所有在内存里的会话**都订阅它的会话流，不只是打开的那个。
- 核心在 `error` 之后、在询问被作废 / 顶替之后**都不发** `session.state`——头据此自己落回休止，
  再拉一次 `/sessions` 对账；对账时比事件旧的快照不覆盖事件。
- `retry.attempt`：演奏条变成「重奏 N/10」+ 原因 + 倒计时（用核心给的 `delayMs`，不自己算曲线）；
  同一次调用的重试在时间线上合成一条记号，用尽后由 `error` 接手。
- 用量口径（核心 `d1c0895`）：`inputTokens` 是**未命中输入**，全部输入 = `inputTokens + cacheReadTokens`；
  命中率用核心给的 `cacheHitRate`（分母只算报了缓存的调用）。上下文仪表读的是全部输入。
- 上下文仪表的满刻度固定按 1M 窗口（核心不报窗口大小），只是刻度。
- **联网是两道闸**：调音台的 `network` 轴（`off|search|fetch|all`，每会话）决定这个会话能碰哪类联网工具；
  后台「联网」页是设备级的凭据 / 端点 / 上限。轴开着但后台未启用（或权限档位不允许消耗型工具）时，
  工具卡会说明是哪一道闸。
- **shell 与 `delete` 同级**（高危 / `Destructive`）：`standard` 及以下**硬拒**、`authorized` 问一句、
  `trusted` 才直接放行。后台「Shell」页只管设备级的三件事（总开关 / `sh` 路径 / 超时），
  「这个会话能不能跑命令」永远在调音台的权限轴上。工具卡上是 `❯ shell <第一行命令>`，完整脚本在展开后的参数原文里。
  调音台会直接写出原因，不让人对着「拨了没反应」猜。`web_search` / `web_fetch` 的请求与结果都走普通工具卡。
- **goal 模式**：主动性轴拨到 `goal` 后，模型停回合而目标未收时核心会自动续跑；会话行与标题栏出现
  「⚑ 目标」chip。结束靠模型调 `finish_goal`——它只把轴拨回 `standard`，拨回后还会多跑一步让模型收尾。
  用户点停止是真停（目标仍在，下次发话或「推进」才继续）；不设步数上限。
- **后台任务**（核心 2026-10-27）：`shell` / `dotnet_build` / `dotnet_test` 的 `background: true` 起的是
  **真进程**，立刻返回 `job-…`；`jobs` / `job_output` / `job_kill` 是模型侧的三个工具，`wait(task=…)` 是等它。
  头的这一侧：
  - 调音台的**任务**页签读 `GET /sessions/{id}/jobs`（结构化），**停止**发 `job.kill`（有回执、有拒绝理由）。
    输出按字节窗口读 `GET /sessions/{id}/jobs/{jobId}/output?offset=`，**累积显示**而不是「后一段盖掉前一段」
    ——`job_output` 是窗口，不是文件，覆盖式显示会让人把中段当成开头。
  - 轮询有三条闸：有任务在跑、或者正看着那个页签、并且页面没被隐藏；打开会话时只拉一次。
    舞台头部与**顶栏**的「⏳ N 在跑」两格读同一份数据（`jobsSummary`，`model.js` 不另存一份），点了跳过去。
  - **核心没有任务事件**：任务结束只表现为会话流上一对合成调用（`job_output` 的自动回报，callId 就是
    `job-…`）。所以时间线不需要新代码——它按普通工具卡配对画；头只在每次工具结果后叫一声，
    由任务面板自己决定要不要重拉（400ms 去抖）。
  - 工具结果里出现 `job-…` 时，卡上多一条「在任务面板里打开」——那是从「我刚起的任务」到「它现在怎么样」
    之间唯一不靠翻菜单的路。
  - ⚠️ 停止**不受模型权限轴管**（核心的裁定：撤回类动作放低门槛）：模型把权限拨到 `off` 之后，
    用户仍然停得掉自己机器上的进程。头如实照做，不额外加一道闸。
- **markdown 表格**（`md.js` 的 `table()` + `.md-table`）：每行一律裁/补到表头宽度（GFM 同款）——
  `<td>` 数不齐时浏览器会把网格撑歪，行一多就整张表错位；整列都是数字时给 `th` / `td` 加 `.num`
  （右对齐 + 等宽数字，不然一列数字得一位一位数才能比大小）。表格是**不透明卡片**：`.score-scroll`
  背后是 64px 一格的五线谱，表格没有底时谱线会从行间穿过去，跟表格自己的横线混成一套「线」——
  哪条是表格的、哪条是纸的，谁也读不清；底一盖，谱线在卡片里断掉，剩下的线就都归表格。
  卡片宽 `fit-content`（两列小表不被拉成一整行，大表填满列宽再横向滚）、高 `min(62vh, 560px)` +
  表头 `sticky`（行多时表头跟着走）；行分隔用斑马纹 + 列间竖细线，不横竖都画满（横线多了会跟谱线一起变噪点）；
  `word-break: keep-all` 让中文不逐字断行（「通过」不会竖成两行）。
- **访问 token 只在核心开了鉴权时才有存在感**：默认（不校验）时页面一条请求都不多带、不弹闸，
  状态栏也因为 `authRequired:false` 不占那一格。开了之后：**反代模式下由进程交**（`auth=head`，
  页面一条都不带；401 只弹横幅，因为页面修不了它）；**直连模式下由页面交**
  （HTTP 走 `Authorization: Bearer`、WS 与图片走 `?token=`；401 一律先清掉本机存着的那份再弹闸——
  核心每次启动都换 token，留着旧的那份只会让人以为「已经填过」）。判据都是 `/info.authRequired`，
  **不是**「`/info` 是不是失败」：未授权时它照样回 200，只是不交本机路径那几格。
- **WS 白名单是模式，不是逐字相等**（核心 `2026-11-05` 起）：默认 `http://*:<头端口>`，主机名通配、
  端口钉死。于是 `localhost` 与 `127.0.0.1` 都能用，换一台设备用局域网地址打开也能用；
  而随便一个网页（端口对不上）照样进不来。头这边有一份**最小镜像**（`js/core.js` 的 `originMatches`，
  与核心 `OriginMatcher` 同一套判据），用途仅限「把话说对」——真正拦人的是核心。
  ⚠️ **这条只在直连那一档成立**：反代模式下握手是 Cadenza 的进程发的，它**不带 `Origin`**，
  核心对无 Origin 的客户端一律放行 ⇒ 白名单整条不适用（后台「系统」页那一格就是这么写的）。
  这不是「绕过了安全」，而是换了个握手的人：能碰到 `/core` 的人＝能打开这个页面的人，那道闸
  现在守在头的 `-Bind` 与核心的 `LILARA_AUTH` 上。
- **归档会话的拉法是分开的**（核心 `b1d6df9` 起）：`GET /sessions` 只给**未归档**的那些，归档那份走
  `GET /sessions/archived`（行形状逐字相同，`archivedAt` 有值）。所以「一个端点拿全 + 本地过滤」的旧写法
  在新核心上会一条归档都画不出来：节目单默认**一条归档都不拉**，勾上「显示已归档」才多打一次那个端点；
  行的 `archivedAt` 会跟本机记的那一份对账（在别的窗口归档/取消归档过，这是唯一会对上的地方）。
  旧核心没有那个端点 ⇒ **404 按旧行为退回**（归档的仍混在 `/sessions` 里，靠行自带的 `archivedAt` 藏）。
  打开一条不在列表里的会话（归档的、或从时间线点进来的已归档子会话、或重开页面恢复上次那一场）时，
  行由 `GET /state` 快照补（`seedRowFromSnapshot`），不当成「会话不存在了」。
- **流式输出**（核心 `3819e74` 起）：开关在**提供商**上（`streaming`，默认关），不在会话上——
  上游吐不吐字是端点能力，同一场会话里换个提供商就该换一种行为。开着的核心会发 `term.delta`
  （`{ turn, blockIndex, deltaKind: text|reasoning, text }`，约 50ms 攒一批），头把它画成一条
  **临时气泡**（`.msg.live`，「正在说…」）：
  - ⚠️ **它只供显示，不是事实**：核心在步末照旧发 `message.appended`，那一条才是权威。
    头见到它就**整块丢掉**临时气泡（`timeline.clearLive`）——少画一段、多画一段都不影响记录；
    这些帧核心也**不保留、不补发**（`Publish(retained:false)`），所以断线重连拿不到半截正文，
    也不会画出两条重叠的气泡。
  - 临时气泡在四个地方一定会消失：收到最终消息、`session.step.begin`、`session.step.end`、
    `session.state` 落回非 Running、以及 `error`（拒绝/出错的步不落模型消息，留着就是对没发生的事撒谎）。
  - 思考与正文按 `blockIndex` + `deltaKind` 分成不同的格，次序跟最终气泡一致（先想、再说）。
  - ⚠️ **工具参数不进增量**（半截 JSON 没有显示价值）：参数由核心逐字拼回，工具的形态一个字没变。
  - ⚠️ **吐过增量就不再重试**：重发会把同一段话在屏幕上再打一遍，而客户端没有撤回语义。
    所以开着流式时，「重奏 N/10」那条退避只在还没吐过字的时候出现。
  - 关着的时候**请求体逐字节不变**（`stream` / `stream_options` 整个键都不出现），这也是它默认关的理由。
- **工具调用与结果按 `callId` 配对，而结果会比调用先到**（核心 `5191592` 起，`2026-11-05`）：
  核心改成「跑完一条报一条」（`tool.result.appended`），而 `tool_use` 所在的**模型消息仍在步末**
  才落盘 ⇒ 一次 `shell` 期间，结果常常比它那条调用早到几秒。头的这一侧：
  - 收到结果却**还没有**那张卡时，**不就地画**「调用不在视野内」的孤儿——那样它会落在**上一条消息**
    后面，看起来就是「这次调用的结果属于上一条消息」，而真正那张卡还在新消息里转「等结果…」
    （用户实测报的正是这个形状）。结果停在 `timeline.parked` 里，等模型消息到了贴到正经那张卡上。
  - 调用**开始跑**就有一条 `tool.call.started`（同样 `retained:false`、重连不补发）⇒ 时间线上先画一张
    **临时的**「执行中」卡（虚线边、「执行中…」，`.toolcall.running`）。理由与临时气泡同一条：
    一次跑五分钟的 `shell` 期间页面上不能一个字都没有。它同样**不是事实**：步末的模型消息一到就整块丢掉。
  - 步边界（`session.step.end` / 下一步的 `step.begin`）是唯一的裁决点：此刻还停在 `parked` 里、
    始终没等到调用的结果，就地画成「调用不在视野内」——那说明那条 `tool_use` 压根没落盘
    （跑到一半被打断就是这条），「没有主人」是事实。⚠️ 别把这一步提前到 `session.state`：
    那是磁盘镜像、每步都发，据此判定会把还在路上的模型消息判成孤儿。
  - ⚠️ **次序是核心的事实，头不许假定**：`WireEvent` 的注释写得很直白（「不要假定模型消息一定先到」），
    所以配对只能靠 `callId`，不能靠「最后一张卡」或者到达次序。

`e2e/` 是一套无依赖的端到端测试：隔离的核心（独立数据根、端口 17989）+ 模拟 OpenAI-chat 上游 +
无头 Chrome（CDP，dotnet 单文件脚本驱动）。不碰 `~/.lilara`。

⚠️ 一整套默认就跑在**反代**这条路上（页面 → `serve.ps1` → 核心）；直连那一档只剩 `17-auth`

## 已知边界

- **长正文曾是「模型一说话页面就死」的真凶（2026-11-15 实测，已按上限处理）**：时间线整条
  `content-visibility: auto`（见 `css/stage.css` 里那份基准），但**正在说的那一条在视口里，跳不过**。
  离线基准（真 CSS + 真 `Timeline.applyDelta`，不断追加一格的正文再读一次 `scrollHeight`）：
  `200 KB 0.1ms / 次 · 1 MB 174ms · 3 MB 595ms · 6 MB 1472ms` ——超线性。核心的增量按 50ms 攒批，
  也就是 20 条/秒 ⇒ 主线程永远画不完，标签页彻底不响应、连刷新都排不上队（用户报的就是这个）。
  现在两处都上了上限：**临时气泡只留最后 128 KB**（它是临时显示，全文在步末落盘的那条消息里，
  卡头上写明了省略了多少）、**落盘正文只排版前 128 KB**，其余按原文放进 `pre.out`（滚动框；
  `Ctrl+F` 与「复制这条」仍是全文；`md()` 2.5 MB 要 675 ms，就是这条的理由）。
  `18-streaming` 末尾两条断言守着它俩。
- **e2e 把「未捕获异常」算失败（`e2e/cdp.cs`，2026-11-15）**：从 `Runtime.exceptionThrown` 计数，
  有就整脚本红、退出码非零。这条是交了学费的——`viz.js` 曾经漏了一个 import，`draw()` 每帧抛一次
  `ReferenceError`，而所有脚本只看 `expect`/`until`，**全绿通过**；那条刷屏把「卡死」的排查带偏了两轮。
  现在输出的每一行都是 `== 0 failed, 0 uncaught`，两个数都得是 0。
  顺带：`js/viz.js` 的 `draw()` 现在包了 try/catch —— 每帧回调抛一次就**停用画布并只报一次**
  （`console.warn`），不再出现「每秒 60 条异常」那种自我刷屏。
- **时间线在页面上最多留 400 条（`Timeline._trim`，2026-11-15）**：更早的从 DOM 里摘掉，顶部留一行
  「更早的 N 条不在页面上」的说明；`seen` 的去重键一并删掉，所以「加载更早的消息」翻回去还能再出现
  （事实在核心那边，删的只是这一页的 DOM）。这是**渲染色天花板**：停摆记录里唯一一直在长的数字就是它
  （36 → 72 → 119 → 160 条 / 1850 → 7405 → 9799 节点）。实测灌 900 条：DOM 稳定在 400 条、节点 11304 → 5304、
  贴底 0 px。⚠️ 它治的是「以后越长越慢」，**不是**当前那几次停摆的原因（那几次只有 119～160 条，没到帽子）。
- **「只剩下音符跳动」= 主线程停了，现场由 `js/watchdog.js` 记下来（2026-11-15）**：卡死时的样子是
  CSS 动画（合成器那一路）还在动，而顶栏那块 canvas（`js/viz.js` 的 rAF）与所有点击全停。
  这种停摆主线程自己报不出来，所以判据放在一条 Worker 上：它每秒看一次「主线程最后一次心跳是多久以前」，
  超过 3 秒就把手里最后一份现场（`tag` + 视图 / 会话数 / DOM 节点数 / 堆 / WS 帧计数 / 可见性 /
  版面与画布尺寸 / 两路心跳）写进 IndexedDB；
  **下次打开页面**时横幅会写「上次运行里主线程停过 N 秒」，点「复制详情」拿全文（同样打在控制台里）。
  记录里有三类东西：
  - `tag`：卡住之前最后启动的那一件事。**分三层**，停摆记录里那一行就是答案：
    1. **里程碑**（节流 250ms）：`evt:*` model 折叠事件 · `tl:*` 时间线合流 · `list` · `open` · `jobs`；
    2. **扇出面包屑（成对）**：`L:list` / `L:head` / `L:about` / `L:perf` / `L:vizphase` / `L:runstate` / `L:status`
       各有对应的 `:out`，末尾还有 `E:sessions`（整段 emit 结束）。判定只看一件事：
       **最后一条是「有 in 没 out」，还是已经出了栈**。有 in 没 out ⇒ 我们的 JS 卡在那一步里。
    3. **帧的三段界线（不节流）**：`Z:task`（这一帧的 JS 退栈 + 微任务跑完）→ `R:frame`（本帧的 rAF 回调开始）
       → `R:frame:out`（**这一帧的渲染步骤回来了**，用 `setTimeout(0)` 卡在它之后）。于是卡死位置只有三种：
       `Z:task` = 微任务之后、下一次 rAF 之前；`R:frame` = **这一帧没走到底**（渲染步骤没回来）；`R:frame:out` = 这一帧跑完了，卡在它之后的任务里。
       ⚠️ 头两版拿 `spin("R:viz")`（节流 150ms）当判据，它会被节流吞掉——「没有 `R:*`」根本不能当结论。
        ⚠️ `R:frame:out` 早先用的是**第二个 rAF**，那只说明「下一帧没来」，分不清「回调里」与「布局里」；
        2026-11-16 08:55 那条记录读到的正是 `R:frame`，判读因此含糊了一回。
       2026-11-15 实测的全序见 `e2e` 之外的那次探针：
       `L:list → S:walk#1 → L:list:out → L:head → L:about → L:head:out → L:perf → L:perf:out →
        L:vizphase → L:vizphase:out → L:runstate → L:runstate:out → L:status → L:status:swap →
        L:status:out → E:sessions`；
    4. **带迭代次数的循环标记**：`S:walk#N` / `S:hiddenStats#N` / `S:filterChain#N` / `md:loop#N` /
       `tl:block#N` / `J:row#N`，定时器 `T:runtime` / `T:perf` / `T:tempo` / `T:title` / `T:counts`（都有 `:out`），
      以及 **rAF 回调** `R:viz#N`（顶栏画布那一圈）/ `R:scroll`（贴底那次滚动）——它们跑在 `Z:task` **之后**，
       所以「最后一条是 `Z:task`」还有一种可能：卡在 rAF 回调里，而不是浏览器的渲染步骤。
       `postMessage` 在调用时就把数据送达 Worker，所以主线程**紧接着**卡死，最后那条也留得住
       （实测：记录里读到 `TEST:spin#42`）。
  - **`?noviz=1` / `?noscore=1`**：分别关掉「顶栏画布那一圈 rAF」与「总谱逐帧订阅」。这两个是**每条 WS 帧
    都要走一遍**的主线程消费者，也是「主线程在一个任务里不出来」最可能的落点。真实环境里二分它们
    （关一个跑一轮）比在这里猜有用：关掉哪个之后不再卡，就锁定哪一块。
  - **`?cv=1`**：给时间线的每一条重新打开 `content-visibility: auto`（2026-11-14 那份基准用的就是它）。
    **默认关着**，理由在 `css/stage.css` 那段注释里：它换来的跳过效果已经由「页面只留 400 条」替代，
    而它自己带着「跳过项高度账 + 锚定 + 每次追加重算 scrollHeight」这一类布局反馈风险——正是
    「JS 退了栈、渲染不返回」的常见形状。实测（关掉它 + 400 条帽子）：一步 40 条工具调用 83 ms、
    40 条结果 2 ms、收尾消息 3 ms、贴底 0 px。
  - 2026-11-15 顺手拆掉的两条**布局反馈回路**（都是「JS 退了栈、渲染不返回」这一类）：
    `.score-scroll` 关掉滚动锚定（`overflow-anchor: none`，贴底由我们自己跟），以及
    `Timeline.scrollEnd()` 不再用 `behavior: "smooth"`（滚动动画每帧重读 `scrollHeight`，而高度随渲染变），
    改为两帧各钉一次（实测贴底 0px）。
  - **`selfDriftMs`**：Worker 自己的 1 秒节拍也被拖了多久。和沉默在同一个量级 ⇒ **整机 / 进程被饿死**
    （核心在跑重活、CPU 或内存被抢光）；节拍准时 ⇒ **沉默只发生在主线程里**。
    ⚠️ 它只回答「机器有没有被抢光」，**不回答「页面是不是在算」**：2026-11-16 之前这里写着「节拍准时
    ⇒ 主线程里有一段长任务，页面在算」，是错的——08:37 那条记录里「前 60 秒最长长任务 128 ms」
    与它直接矛盾。
  - **两路心跳（2026-11-16 加）**：只看定时器这一路，「切后台」和「真卡死」长得一模一样——隐藏页的
    渲染与定时器本来就会被浏览器停掉，而旧心跳还带着 `if (!document.hidden)`（自己停发），于是
    「切走两分钟」被记成「卡死两分钟」。现在定时器心跳（1.5 秒，**隐藏时照发**）与 rAF 心跳
    （每帧一个空回调、500 ms 最多一条消息）分开，记录里多三格：

- **反代这一层是新东西（2026-11-14），它的边界值得逐条记住**：
  - `serve.py` 只在 Linux/macOS 上跑，而**这台开发机没有 python3**（环境明确不让装）⇒ 它的
    HTTP 反代与 WS 隧道是**照着同一份契约写的，但没有在本机跑过一次**。首次在一台有 python3
    的机器上跑时，先看 `curl -s localhost:17990/core/info` 与页面能不能连上。
  - `serve.ps1` 的 WS 中继受 HttpListener 限制：**页面必须请求 `cadenza` 子协议**。用别的客户端
    （curl、脚本）戳 `/core/ws` 时，要么带上这个子协议，要么它直接 400（措辞里写了原因）。
  - 一条 WS 隧道占一个 runspace（池上限 16）。同时开十几个标签页时，第 17 个之后的请求会排队——
    这是池子的问题，不是核心的。
  - 反代**只转字节**：它不看帧、不重试、不排序。所以上游断在半条消息上时，页面看到的是一次断开
    （照旧走重连 + 重新拉快照），不是「半条消息」。
  - 上游的响应是**整份读进内存再回**（不是流式边转）。`/store` 的图片、`/history` 的一页都在几 MB
    以内；真遇到大对象时这一条会变成内存峰值，而不是错误。
- **php / busybox 那两档没有反代**：页面退回直连核心（老行为）。要「由 Cadenza 的进程连核心」，
  那台机器上得有 python3。

- 核心没有改名命令，标题只在建会话时起一次。
- 「工具结果是不是失败」是按结果文本里的关键字猜的（核心不给结构化状态），只影响颜色。
- **全套 e2e 共用一个数据根**（`2-flow` 会清一次，之后每个脚本都往上叠）⇒ 凡是从「整个核心」读数的
